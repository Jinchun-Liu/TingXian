## 决策价值与实现

假设：已有 Rust 时间线能根据原生音频游标和设备时钟生成正确 PCM，通过固定 ABI 交给
同一个 C++ Session，同时保留停止/故障/代次证据。决定是否进入实际端点和共同 owner
集成。错源、过期写入、未固定 DLL、无界缓存、静默错误或意外启动设备均为停止条件。

- 新增 `TingXianAudioOutput.dll` ABI 和 Rust `audio::NativeAudio`，复用既有 WASAPI
  后端，不另写音频协议。原生方法由同一线程调用；Rust 类型禁止 Send/Sync，DLL 检查
  线程归属。固定大小/版本、独立生命周期、内嵌 NUL/长度、HRESULT 和回调寿命检查。
- 自有 DLL 使用原生宿主构建摘要及文件/父目录租约，系统目录查依赖；不接受网页设置
  提供的路径或临时计算的“信任摘要”。测试对自有构建产物计算摘要不等于产品 pin 流程。
- 时钟先取得两次前进观测。采样帧游标通过 `interval_from_frame` 精确映射，保留分数
  设备单位；不先做 `frame * frequency / rate` 的整数截断。44100 单位/秒的合成例中，
  第 481 帧应对应 100208 个 100 ns tick，提前取整会变成 100000；相邻输出区间现在
  在有理数设备坐标上严格相接，仍保留旧设备位置接口。
  产品路径在设备观测返回后读取实际 QPC，避免使用调用前的 UI 时间导致新观测被误判为
  “来自未来”；固定时间注入仅编译于测试，不能由产品调用方选择。
- 每张票据绑定不可复用的对象身份、代次和序号，销毁后即使 native 地址/代次重复也
  不会接收旧票据。S_FALSE 只代表背压；不消耗输入、不给空票据。Stop/Reset 两类错误、
  客户端清空、外部排空未知分开返回；通知标记不能冒称两路实际停止。
- 单独的 `TingXianAudioFixture.dll` 只构造内存后端；Step/Read 导出不进入产品 DLL。
  真实 DLL 本轮只加载、检查 ABI/导出，并拒绝不存在的配对 ID，不打开音频客户端。

## 接线暴露的满幅问题及修复

原声输入严格在 [-1,1] 内仍可能产生滤波过冲；追加的满幅合成方波回归实测峰值
**1.17415130**，导致原生输出约定拒绝有效原声，原始失败日志 `peak-before.log` 保留。
根因是滤波浮点中间结果未经最终输出范围转换。修复仅在 sinc 最终输出处饱和到
[-1,1]，不改滤波系数/历史、增益或输入验证，不放宽原生 NaN/越界断言。

同一回归修复后峰值 **1.0**，报告 **240/480** 个饱和样本；这是特意构造的满幅
方波，不是正常语音质量比例。`RenderedWindow` 和 `Metrics` 均记录 `saturated_samples`。
范围内样本不变；饱和可能带来峰值失真，后续实测需看计数与听感，不能称无损音频。
另一个跨语言满幅用例核对原生实际缓冲区，确认不再故障，不只是 renderer 返回成功。

## 尚未完成

这一步接通音频原生调用边界，未形成实时共同音视频 owner。当前 v1 视频仍以毫秒采集
租约和请求时刻供帧，不能把它包装成支持共同 QPC/计划呈现 PTS。下一步要明确 v2 能力、
两路预留/提交/异常撤销、事件等待和跨对象/进程保留的排空门槛，再接主窗。

实际虚拟线缆写入/录音侧接收、排空后重启、物理输入、SDK 效果、普通用户安装版、
飞书接收端偏移 P95 ≤100 ms 与长期会议均未通过本轮验收。不会以 DLL 加载、内存
PCM 正确或回调中的视频标签替代会议接收。第三方驱动/模型未打包，商业分发仍独立核实。
