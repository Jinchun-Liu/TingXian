# Windows 本地转写与会议朗读稿

全部人物、业务和事故均为合成测试情境，不代表使用者的真实经历。先取得播放与采集许可，使用耳机；本地阶段关闭 AI 外发，调用数应始终为 0。对端段落由第二台设备/对端朗读，本人段落只对本机麦克风朗读，不在同一个扬声器混播。

## 短测假设与停止规则

假设：当前安装版可将系统输出记为对方、麦克风记为本人，并在启停和恢复后保持来源及设置。结果决定是否进入真实 AI 和长会议验收。任一来源混淆、非预期外发、无法停止、记录丢失或恢复自动采集，立即停止该轮，保存失败证据并定位；不靠重复测试稀释失败。

## 第一轮：来源与术语

对方：这是系统输出来源测试。请说明 StockMarketAgent 的契约测试怎样区分 JSON 字段缺失、null、数字零和空字符串。JSON Schema 校验通过，是否就意味着业务语义正确？请保留否定词：零不是缺失，null 不一定等于空字符串。

本人：这是本人麦克风来源测试。我会先检查 JSON Schema，再检查业务语义。我提出的是测试设计，没有声称自己处理过真实生产事故。对于幂等性，我会使用租户标识与幂等键的联合约束。

对方：你刚才说的联合约束，怎样处理并发竞争和过期重试？请引用本人实际说过的方法，不能把尚未读出的 AI 草稿当作本人回答。

核对：两路来源各自正确；关闭“记录我的声音”后本人不再进入转写，对方仍可转写；调用数 0。停止再启至少三次，每轮换一个唯一标记：青松一号、白鹭二号、星河三号。逐轮记录真实文字，不能只记录流已启动。

## 第二轮：连续长题（按自然语速约两分钟，以实际时长为准）

我们现在讨论一个虚构的 StockMarketAgent 服务。它通过 FastAPI 接收股票研究任务，返回 JSON 格式的结果。请先设计契约测试，明确哪些要求应该交给 JSON Schema，哪些要求属于业务语义。假设结果包含 price、volume、currency、analysis 和 request_id。price 字段缺失、price 为 null、price 为数字零、price 为字符串零以及 price 为空字符串，是五种不同情况。请分别说明预期行为，不要为了通过测试把它们统一转换为同一个值。对于 volume，零可能表示当前时段没有成交；对于 currency，如果接口约定必须提供币种，缺失和空字符串都不能被默认值悄悄掩盖。

接下来考虑重试。租户甲和租户乙使用相同的幂等键，但提交的业务任务不同。你怎样设计唯一约束，避免把两个租户的任务误判为重复？如果同一租户重复使用同一个幂等键，却传入不同的请求体，系统应该返回先前结果、拒绝冲突，还是创建新任务？请给出明确规则和验证方法。

再加入并发和超时。两个请求几乎同时到达，事务已经提交，但响应在返回客户端前超时。客户端收到 HTTP 504 后重试。请注意，超时不等于事务回滚，重试成功也不等于只执行过一次。你需要哪些数据库记录、事务证据、事件日志或唯一约束，才能判断没有重复写入？如果外部通知已经发送，而本地状态还没有更新，又该怎样限制重复副作用？请说明事务发件箱或其他机制的适用边界，不要把“自动重试”当作完整答案。

最后请给出 pytest 的测试组织方式，分别覆盖正常请求、字段缺失、null、零、空字符串、并发争用、事务提交后超时、重复请求体和冲突请求体。哪些断言可以只看 HTTP 响应，哪些必须检查数据库或日志？哪些结论只能称为故障注入演练结果，不能写成本人实际处理过的生产事故？请先提供答案正文，再给出纠正后的完整问题，并覆盖所有子问题。

本人：我确认采用租户标识和幂等键的联合唯一约束，同时保存请求体摘要。事务提交后超时的请求，重试时先读取既有状态；相同键但不同摘要应显式冲突。这是我现在提出的方案，不是过往经历。

对方：如果两个请求都先查到记录不存在，随后同时插入，你刚才的方案怎样避免竞态？如果幂等键已经过期，但旧任务仍在执行，你会怎样处理重试？

## 30 题 / 约 60 分钟会议顺序
